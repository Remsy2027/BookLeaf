# Approach and trade-offs

I prioritized a complete, explainable support flow: an author can log in, inspect the supplied book records, submit a query, and see the team's response without refreshing. Admins get an urgency-ordered queue, relevant book context, editable classification and priority, an unsent draft, status controls, assignment and private notes. The interface keeps policy guidance beside the reply composer so an API outage does not become a support outage.

The application uses React for focused UI components, Express for a conventional REST API, and SQLite for persistent local operation without an external database service. Ownership is enforced in the API, never trusted to frontend filtering. Session tokens are opaque, hashed at rest and sent in HttpOnly cookies. Author responses deliberately omit private notes and drafts. Version checks prevent concurrent admin edits from silently overwriting each other.

AI is advisory. Category and priority use one strict structured-output call. Drafting sends only the selected policy, book facts and a bounded public conversation history. The prompt distinguishes verified account facts from missing bank, accrual and production information, and disallows invented payout dates or claims of completed work. Every draft remains subject to human review. Timeouts, validation failures and rate limits lead to clearly labelled fallback triage and manual writing. Tickets are stored before the provider is called. Lazy generation, bounded context, cached drafts and a short circuit breaker control unnecessary spend.

I chose polling over WebSockets to keep deployment and debugging straightforward. SQLite and process-local limits suit a single-instance evaluation, but they are deliberate limits. File uploads are represented honestly as unavailable rather than suggesting that a selected file was stored. The supplied financial snapshots are retained exactly; the application does not fabricate a sales ledger or calculate payout promises from incomplete data.

To evolve this into a production system, I would introduce PostgreSQL migrations, a durable queue for AI tasks, request idempotency, an audit trail, an evaluated prompt/model dataset, shared rate limits and observability. Next would come unique author invitations, account recovery, attachment storage with validation and scanning, visibility-aware polling or SSE, and real royalty/production integrations. Deployment should include HTTPS, private source access and scheduled database backups. A small live Groq evaluation now covers six classification cases and two policy-grounded draft cases, with an additional Chrome draft check. A hosted end-to-end check remains necessary before calling the submission fully deployed.
